# MyTrails — Journey Map

This catalog is the **hand-off artifact** for MyTrails: every user journey as a
sidebar group of isolated, pinned-state screens. Each story is one exact state —
no clicking through flows to reach it. Developers use it to match pixels and
behavior; the PO uses it to verify every business rule has a visible surface.

> **Devs: check [Build Status](?path=/docs/build-status--docs) first** — it says
> which screens are confirmed (build now) vs still tentative/unconfirmed.

## The 12 journeys

**Act 1 — Runner (public, no login)**

1. **Discover Events** — browse the platform home: grid / list / calendar, region filter, EN/TH.
2. **Explore an Event** — the PYT 2026 microsite and the generic event-preview template.
3. **Register & Pay** — the Direction-2 registration flow on a live event: runner
   form (PDPA consent) → mock payment (Stripe-shaped card or PromptPay QR + slip
   upload) → `MT-XXXXXX` confirmation code → the runner lands in the organizer's
   Orders/Participants, with PromptPay slips queued for verification (see
   Journey 8's slip queue). Plus the public registration lookup page.

**Act 2 — Organizer: from zero to a live event**

4. **Get Started** — login, first look at the dashboard, profile & security surfaces.
5. **Create & Submit Event** — the 5-step wizard (Info → Race Config → Tickets →
   Publishing → Review & Submit) plus the Drafts tab.
6. **Approval Outcomes** — the state machine: `pending_review` → `live` / `scheduled` /
   `rejected` (reason shown in the edit wizard, resubmit loop). Editing a live or
   scheduled event drops it back to `pending_review`. Every outcome (plus payout and
   registration activity) also surfaces in the dashboard's notification bell and as a
   mock email on the outbox page (`/organizer/outbox`).

**Act 3 — Organizer: running a live event**

7. **Run the Event** — race operations, participants, BIB, promotions, broadcast, settings.
8. **Get Paid** — payout account setup and per-event Orders/Finance (2-part commission).

**Act 4 — Admin: running the platform**

9. **Moderate Events** — approvals queue + full event review (approve / reject with
   reason / commission override / force unpublish).
10. **Platform Finance** — the payout queue (`held` → `payable` → `paid`).
11. **Platform Administration** — overview, organizer accounts, tiers & settings.

**Extras**

- **Design System** — the source of truth for look & feel: token pages (Colors /
  Typography / Surfaces) plus interactive component docs (Button, Badge, Input,
  Tabs, Dialog, StatusBadge, EventCard) with props tables and live Controls.
  Reference for developers; PO can skip.
- **System** — the 404 page and future error states.
- **Experiments (not for build)** — the original Direction-2 order-flow screen,
  kept as the visual reference the registration flow (Journey 3) was built from.
  Not part of any build.

## Conventions

- **1 journey = 1 user goal; 1 story = 1 pinned state.** Screens are pinned via
  optional `initial*` props (default = live-app behavior) or `<Routes location>`
  for pages that read the URL.
- Data comes from the shared `EventsProvider` store, seeded with events covering
  **every** status — tabs and queues are populated out of the box.
- After editing stories run `npm run storybook:deploy` to refresh the live catalog
  at `mytrails.theingress.co/journey`.
